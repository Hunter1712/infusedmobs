# 1.21.1 Loom mappings research

We need `:1.21.1` (obfuscated, Java 21) to compile the same MojMap `common` sources as `:common`/`:26.2` (unobfuscated, Java 25). We decided `:1.21.1` applies `net.fabricmc.fabric-loom-remap` with `mappings loom.officialMojangMappings()` plus `modImplementation` loader/Fabric API, and every 26.x-only API in `common` goes behind a same-FQN per-version shim, because Loom's obfuscation mode is per-project and a remap project is the only setup that serves MojMap-named Minecraft plus remapped mods, at the cost of rewriting the four 1.21.1 shims that were copied verbatim from 26.2.

## 1. Plugin IDs per subproject

- `net.fabricmc.fabric-loom` is for non-obfuscated versions (Minecraft 26.1+); `net.fabricmc.fabric-loom-remap` is for obfuscated versions (Minecraft 1.21.11 and older); `fabric-loom` is legacy; `net.fabricmc.fabric-loom-companion` is for non-Loom subprojects in multi-project setups. (Source: https://docs.fabricmc.net/develop/loom — "Plugin IDs")
- The same IDs are registered in Loom's own build: `net.fabricmc.fabric-loom` -> `LoomNoRemapGradlePlugin`, `net.fabricmc.fabric-loom-remap` -> `LoomRemapGradlePlugin` (an alias that just applies `fabric-loom`), legacy `fabric-loom` -> `LoomGradlePlugin`, plus `net.fabricmc.fabric-loom-companion`. (Source: https://raw.githubusercontent.com/FabricMC/fabric-loom/dev/1.17/build.gradle — `gradlePlugin { plugins { ... } }` block)
- Applying the no-remap ID forces that project into non-obfuscated mode: `LoomGradleExtensionImpl` sets `disableObfuscation=true` (finalized) when `LoomNoRemapGradlePlugin` is present, otherwise it reads the `fabric.loom.disableObfuscation` property. (Source: https://raw.githubusercontent.com/FabricMC/fabric-loom/dev/1.17/src/main/java/net/fabricmc/loom/extension/LoomGradleExtensionImpl.java — constructor)
- `loom.officialMojangMappings()` throws `UnsupportedOperationException("Cannot use Mojang mappings in a non-obfuscated environment")` exactly when that project's `notObfuscated()` is true. (Source: https://raw.githubusercontent.com/FabricMC/fabric-loom/dev/1.17/src/main/java/net/fabricmc/loom/extension/LoomGradleExtensionApiImpl.java — `officialMojangMappings()`)
- Obfuscation mode is per-project extension state, so the root applying (or not applying) `fabric-loom` cannot flip a subproject's mode; the reported error means the `1.21.1` project itself evaluated the mappings call while in no-remap mode (wrong plugin ID at the time), not root interference. (Source: same two files above — `notObfuscated()` reads `LoomGradleExtension.get(getProject())`, i.e. the calling project)
- Root must therefore only *declare* both IDs with `apply false` and never apply Loom to the sourceless root; each subproject applies exactly one: `common`, `26.2`, `1.20.1` use `net.fabricmc.fabric-loom`, `1.21.1` uses `net.fabricmc.fabric-loom-remap`. (Source: repo `build.gradle`, `settings.gradle` pluginManagement pointing at https://maven.fabricmc.net/)
- The obfuscated/unobfuscated boundary is version metadata, not config: `isUnobfuscated()` is true when `releaseTime >= 2025-11-01` AND the version JSON has no `client_mappings` download. (Source: https://raw.githubusercontent.com/FabricMC/fabric-loom/dev/1.17/src/main/java/net/fabricmc/loom/configuration/providers/minecraft/MinecraftMetadataProvider.java — `isUnobfuscated()`; https://raw.githubusercontent.com/FabricMC/fabric-loom/dev/1.17/src/main/java/net/fabricmc/loom/util/Constants.java — `RELEASE_TIME_1_21_11_UNOBFUSCATED_SNAPSHOTS`)
- `1.21.1` is on the obfuscated side: `releaseTime 2024-08-08`, `javaVersion.majorVersion 21`, downloads include `client_mappings` + `server_mappings`. (Source: https://piston-meta.mojang.com/v1/packages/81396eb81dcfec06cf6fa1c6fa06e4ab0c15eb81/1.21.1.json)
- `26.2` is on the unobfuscated side: `releaseTime 2026-06-16`, `javaVersion.majorVersion 25`, downloads are only `client` + `server` (no mappings). (Source: https://piston-meta.mojang.com/v1/packages/987b91a95ae93b3bb78cc14d6e0bbd31bad08d59/26.2.json)

## 2. Mappings and dependency configurations for `:1.21.1`

- `mappings loom.officialMojangMappings()` is the correct declaration for the 1.21.1 remap project; it is shorthand for `layered { officialMojangMappings() }` and downloads Mojang's `client.txt`/`server.txt` from the version manifest, dropping non-intermediary roots via the intermediary layer. (Source: `LoomGradleExtensionApiImpl.officialMojangMappings()`; https://raw.githubusercontent.com/FabricMC/fabric-loom/dev/1.17/src/main/java/net/fabricmc/loom/configuration/providers/mappings/mojmap/MojangMappingsSpec.java; https://raw.githubusercontent.com/FabricMC/fabric-loom/dev/1.17/src/main/java/net/fabricmc/loom/configuration/providers/mappings/mojmap/MojangMappingLayer.java)
- The `layered() { officialMojangMappings() ... }` form is only needed to stack extras (e.g. Parchment); the shorthand suffices here. (Source: https://docs.fabricmc.net/develop/loom/options — `dependencies` reference block; https://raw.githubusercontent.com/FabricMC/fabric-loom/dev/1.17/src/main/java/net/fabricmc/loom/api/mappings/layered/spec/LayeredMappingSpecBuilder.java — `officialMojangMappings()` overloads)
- Layered MojMap resolution for 1.21.1 is proven working in this repo's own Gradle cache (`~/.gradle/caches/fabric-loom/1.21.1/loom.mappings.1_21_1.layered+hash.2198-v2`), so the current `1.21.1/build.gradle:27` mappings line is right and must be kept, not removed. (Source: local Gradle cache listing; repo `1.21.1/build.gradle`)
- Yarn `1.21.1+build.3` exists but must NOT be used: both Yarn and MojMap occupy the `named` namespace and `common` is written in MojMap, so Yarn would force translating every shared source. (Source: https://maven.fabricmc.net/net/fabricmc/yarn/maven-metadata.xml — `1.21.1+build.3`; https://raw.githubusercontent.com/FabricMC/fabric-loom/dev/1.17/src/main/java/net/fabricmc/loom/api/mappings/layered/MappingsNamespace.java — `NAMED` docs)
- Fabric Loader and Fabric API in the remap project must use `modImplementation` (not `implementation`): only `mod*` configurations are remapped to the project's `named` (MojMap) mappings; plain `implementation` bypasses `ModConfigurationRemapper`. (Source: https://docs.fabricmc.net/develop/loom — "Dependency Configurations" (`modImplementation` "will be remapped to match the mappings"); https://raw.githubusercontent.com/FabricMC/fabric-loom/dev/1.17/src/main/java/net/fabricmc/loom/configuration/LoomDependencyManager.java — `handleRemapDependencies` vs `handleNonRemapDependencies`; https://raw.githubusercontent.com/FabricMC/fabric-loom/dev/1.17/src/main/java/net/fabricmc/loom/configuration/RemapConfigurations.java — remap options table)
- Without any `mappings` dependency the compile classpath stays intermediary/obfuscated (`axu`-style classes, no `ServerLevel`), matching Loom's pipeline (merged -> intermediary -> mapped jars). (Source: https://docs.fabricmc.net/develop/loom — "Development Environment Setup")
- The `class_1297`/`class_2168` errors are intermediary names leaking through un-remapped Fabric API: `class_1297` = `Entity`, `class_2168` = `ServerCommandSource`, `class_1309` = `LivingEntity`. (Source: `mappings/mappings.tiny` inside https://maven.fabricmc.net/net/fabricmc/yarn/1.21.1+build.3/yarn-1.21.1+build.3-v2.jar)
- Both pinned Fabric API versions exist: `0.116.6+1.21.1` and `0.155.2+26.2`. (Source: https://maven.fabricmc.net/net/fabricmc/fabric-api/fabric-api/maven-metadata.xml)
- Keep `enableTransitiveAccessWideners = false` in `:1.21.1`: FAPI access wideners target intermediary and the project compiles against MojMap `named`, same rationale as the existing `1.20.1/build.gradle:22-23` comment. (Source: repo `1.20.1/build.gradle`; https://docs.fabricmc.net/develop/loom/options — `enableTransitiveAccessWideners`)

## 3. API deltas 1.21.1 vs 26.2 (Mojang `client.txt` for 1.21.1 vs 26.2 merged jar via `javap`)

All 1.21.1 MojMap claims below are from https://piston-data.mojang.com/v1/objects/2244b6f072256667bcd9a73df124d6c58de77992/client.txt (line numbers cited); all 26.2 claims from `javap` on `~/.gradle/caches/fabric-loom/26.2/minecraft-merged.jar` (the unobfuscated Mojang artifact, so class/method names are MojMap verbatim).

- Dimension accessor: 1.21.1 has `ResourceKey#location()` returning `ResourceLocation` (client.txt:53769); 26.2 has `ResourceKey#identifier()` returning `Identifier`, `Identifier` exists, `ResourceLocation` does not exist at all. (Source: client.txt `ResourceKey` block; `javap net.minecraft.resources.ResourceKey`, `net.minecraft.resources.Identifier`)
- Repo impact: `1.21.1/.../tier/DimensionHelper.java` calling `identifier()` is wrong for 1.21.1 and must call `location()`; the 26.2 copy stays as-is.
- Spawn reason: 1.21.1 has `MobSpawnType` (with `REINFORCEMENT`, `COMMAND`) and `EntityType#create` only as 6-arg `(ServerLevel, Consumer, BlockPos, MobSpawnType, boolean, boolean)` (client.txt:74028) or 1-arg `(Level)` (client.txt:74045+179) — no 2-arg `(Level, reason)` overload; `EntitySpawnReason` occurs 0 times. 26.2 has `EntitySpawnReason` (with `REINFORCEMENT`, `COMMAND`) and `create(Level, EntitySpawnReason)`. (Source: client.txt `EntityType`/`MobSpawnType` blocks; `javap net.minecraft.world.entity.EntityType`, `net.minecraft.world.entity.EntitySpawnReason`)
- Repo impact: `1.21.1/.../util/SpawnHelper.java` is wrong twice (wrong enum, nonexistent overload); rewrite against the 6-arg `create` with `MobSpawnType`.
- Damage: 1.21.1 `LivingEntity` (and siblings) expose only `hurt(DamageSource, float)`; `hurtServer` occurs 0 times. 26.2 exposes `hurtServer(ServerLevel, DamageSource, float)`. (Source: client.txt (`boolean hurt(...)` lines e.g. 74658; `hurtServer` count 0); `javap net.minecraft.world.entity.LivingEntity`)
- Repo impact: `1.21.1/.../util/AbilityHelper.java` `reflectThorns`/`hurtFromExplosion` must call `hurt`; its `damageArmor` 4-arg `hurtAndBreak(int, ServerLevel, ServerPlayer, Consumer)` is valid in BOTH versions (client.txt:92279; `javap net.minecraft.world.item.ItemStack`), so only the `hurtServer` lines change.
- Persistence: 1.21.1 `SavedData` uses `save(CompoundTag, HolderLookup.Provider)` + `SavedData$Factory(Supplier, BiFunction, DataFixTypes)`, consumed via `DimensionDataStorage#computeIfAbsent(Factory, String)` (client.txt:123053-123068, 123398-123412); `SavedDataType` occurs 0 times. 26.2 uses `SavedDataType(Identifier, Supplier, Codec, DataFixTypes)` record + `computeIfAbsent(SavedDataType)`. (Source: client.txt `SavedData`/`DimensionDataStorage` blocks; `javap net.minecraft.world.level.saveddata.SavedDataType`; https://docs.fabricmc.net/develop/serialization/saved-data — `SavedDataType` + `CODEC` + `computeIfAbsent(TYPE)` sample)
- Repo impact: `1.21.1/.../tier/TierSavedData.java` (currently a 26.2 copy using `SavedDataType`/`Identifier`) must be rewritten to the `Factory` + `CompoundTag` model.
- Gamerules: 1.21.1 vanilla is `net.minecraft.world.level.GameRules` with `Key`/`Type` (175 occurrences; `gamerules` subpackage occurs 0 times); Fabric's 1.21.1 API registers via `GameRuleRegistry.register(name, category, type)` with types from `GameRuleFactory`. 26.2 vanilla is `net.minecraft.world.level.gamerules.{GameRule, GameRuleType, GameRuleCategory, GameRuleMap}` (with `GameRuleMap.TYPE`); Fabric's 26.2 API registers via `GameRuleBuilder...buildAndRegister(Identifier)`. (Source: client.txt `GameRules` block at 97839; `javap net.minecraft.world.level.gamerules.GameRuleMap`; https://raw.githubusercontent.com/FabricMC/fabric/1.21.1/fabric-game-rule-api-v1/src/main/java/net/fabricmc/fabric/api/gamerule/v1/GameRuleRegistry.java + `GameRuleFactory.java`; https://raw.githubusercontent.com/FabricMC/fabric/26.2/fabric-game-rule-api-v1/src/main/java/net/fabricmc/fabric/api/gamerule/v1/GameRuleBuilder.java)
- Repo impact: `1.21.1/.../gamerules/ModGameRules.java` (currently a 26.2 copy) must be rewritten to `GameRuleFactory` + `GameRuleRegistry` returning `GameRules.Key`.
- Command args: 1.21.1 has `ResourceLocationArgument` (`id()` factory, `getId(ctx, name)` returning `ResourceLocation`; client.txt:34989-35005) and `ResourceArgument.getSummonableEntityType` (client.txt:34914); `IdentifierArgument` occurs 0 times. 26.2 has BOTH `IdentifierArgument` (`id()`/`getId` returning `Identifier`) and generic `ResourceArgument`. (Source: client.txt argument blocks; `javap net.minecraft.commands.arguments.IdentifierArgument`, `net.minecraft.commands.arguments.ResourceArgument`)
- Repo impact: `common/.../command/InfusedMobsCommand.java` uses 26.2-only `IdentifierArgument` + `dimension().identifier()`; either add a command-arg shim or version-split the command file, since `Identifier` vs `ResourceLocation` return types leak into signatures.
- Mixin target is safe across both: `getExperienceReward(ServerLevel, Entity)` exists with the identical descriptor in 1.21.1 and 26.2, and the mixin captures no target args. (Source: client.txt:74604; `javap net.minecraft.world.entity.LivingEntity`)
- `org.spongepowered` missing is a dependency-wiring symptom, not a missing repository: sponge-mixin ships transitively via the loader (present in the local module cache as `net.fabricmc:sponge-mixin`), and Loom additionally adds `fabric-mixin-compile-extensions` as `annotationProcessor` plus Mixin AP args on every `JavaCompile`. Declaring loader/FAPI with plain `implementation` in a remap project skips Loom's remap wiring, which starves the AP/compile classpath. (Source: local `~/.gradle/caches/modules-2/files-2.1/net.fabricmc/sponge-mixin`; https://docs.fabricmc.net/develop/loom — "Default Configuration" (annotationProcessor + Mixin AP); https://raw.githubusercontent.com/FabricMC/fabric-loom/dev/1.17/src/main/java/net/fabricmc/loom/configuration/CompileConfiguration.java — `setupMinecraft`/`setupMixinAp`)

## 4. Sharing `common` sources into the remap project

- `srcDir "${rootProject.projectDir}/common/src/main/java"` sharing is mappings-unaware file inclusion, so it is supported only when every shared file compiles under both MojMap variants; anything touching the deltas above must live in same-FQN per-version shims (the existing `DimensionHelper`/`SpawnHelper`/`AbilityHelper` pattern), never in `common`. (Source: repo `1.21.1/build.gradle` + `26.2/build.gradle` `sourceSets` blocks)
- `namedElements` project dependencies are NOT an alternative here: the configuration is only registered when `!disableObfuscation()`, and it carries that project's own MC-version `named` output — a single `common` Loom project (26.2, no-remap) has neither a `namedElements` variant nor 1.21.1-named bytecode to offer. (Source: https://raw.githubusercontent.com/FabricMC/fabric-loom/dev/1.17/src/main/java/net/fabricmc/loom/configuration/LoomConfigurations.java — `NAMED_ELEMENTS` registration; https://docs.fabricmc.net/develop/loom — "Depending on Subprojects" (`namedElements`) vs https://docs.fabricmc.net/develop/loom/classpath-groups — "Sub Projects" (`fabric-loom-companion` for non-Loom projects))
- Verdict: keep `srcDir` sharing, fix the four 1.21.1 shims (`DimensionHelper`, `SpawnHelper`, `AbilityHelper` hurt paths, `ModGameRules`, `TierSavedData` — five files counting both helpers), and extract the `Identifier`/`ResourceLocation` command-arg usage out of `common` `InfusedMobsCommand` into a shim; do not introduce `namedElements` between `common` and version projects.

## Recommended `:1.21.1` dependencies block

```groovy
dependencies {
    minecraft "com.mojang:minecraft:${project.minecraft_version}"
    mappings loom.officialMojangMappings()
    modImplementation "net.fabricmc:fabric-loader:${project.loader_version}"
    modImplementation "net.fabricmc.fabric-api:fabric-api:${project.fabric_api_version}"
}
```

- `mappings loom.officialMojangMappings()` compiles `:1.21.1` (a remap project) against MojMap `named`, matching `common` sources. (Source: `LoomGradleExtensionApiImpl.officialMojangMappings()`)
- `modImplementation` (not `implementation`) remaps loader/FAPI to `named` so their Minecraft-referencing signatures stop leaking `class_*` intermediary names. (Source: https://docs.fabricmc.net/develop/loom — "Dependency Configurations")
