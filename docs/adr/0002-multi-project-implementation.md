# Multi-project implementation with Gradle subprojects and shims

We implemented ADR 0001's decision as `common` + `1.20.x`/`1.21.x`/`26.x` Gradle subprojects (`settings.gradle:12`) with `common/src/main/java` shared via `sourceSets { srcDir "${rootProject.projectDir}/common/src/main/java" }` (`26.x/build.gradle:32`) and version-specific shims (`gamerules/ModGameRules.java`, `tier/TierSavedData.java`, `fabric.mod.json` with `~mc` and `java >=17/21/25`, `infusedmobs.mixins.json` with `JAVA_17/21/25`). Artifacts use `mod_version+mc` (`2.8.0+1.20.x` etc) per Q7 A and collects `*/build/libs/` via `./gradlew build`. CI workflow removed 2026-09-24; builds run locally.

We kept `common` compiling against `26.x` for tests (`common/build.gradle:32` pulls `26.x` shims) and made `MobTierManager`/`TierSavedData` Java 17 compatible (pattern-matching `switch` → `instanceof`) so `1.20.x` (`release=17`) builds. Each Versioned Source Set compiles against its own `minecraft`/`fabric-api` with official Mojang mappings (`1.20.x/build.gradle:28`, `1.21.x/build.gradle:27`) — proven by version-only APIs in the adapters (`ResourceLocation`, raw `MobEffect` fields and single-arg `create(Level)` exist only on 1.20.x; `EntitySpawnReason` only on 26.x). In-game proof for the older artifacts is outstanding (release gate); the build proves compilation only.
