# Multi-project implementation with Gradle subprojects and shims

We implemented ADR 0001's decision as `common` + `1.20.1`/`1.21.1`/`26.2` Gradle subprojects (`settings.gradle:12`) with `common/src/main/java` shared via `sourceSets { srcDir "${rootProject.projectDir}/common/src/main/java" }` (`26.2/build.gradle:32`) and version-specific shims (`gamerules/ModGameRules.java`, `tier/TierSavedData.java`, `fabric.mod.json` with `~mc` and `java >=17/21/25`, `infusedmobs.mixins.json` with `JAVA_17/21/25`). Artifacts use `mod_version+mc` (`2.7.1+1.20.1` etc) per Q7 A and CI now builds all JDKs (`build.yml:17-32`) and collects `*/build/libs/`.

We kept `common` compiling against `26.2` for tests (`common/build.gradle:32` pulls `26.2` shims) and made `MobTierManager`/`TierSavedData` Java 17 compatible (pattern-matching `switch` → `instanceof`) so `1.20.1` (`release=17`) builds. Each Versioned Source Set compiles against its own `minecraft`/`fabric-api` with official Mojang mappings (`1.20.1/build.gradle:28`, `1.21.1/build.gradle:27`) — proven by version-only APIs in the adapters (`ResourceLocation`, raw `MobEffect` fields and single-arg `create(Level)` exist only on 1.20.1; `EntitySpawnReason` only on 26.2). Runtime parity across versions is proven in-game, not by the build.
